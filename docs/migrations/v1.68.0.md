# Upgrading to v1.68.0

The auto-approver approves a dependency bot's pull request only when every first-party version it
adds carries a release proof: an attestation over the version's exact bytes, signed by the producer's
`release.yaml` at the version's tag, and an immutable Release of that tag from the org's release App.
Any workflow run of a repository can publish its packages, so a version no release built waits for a
person. The approval and the auto-merge it arms name the checked commit in every mode.

## Do I need to act?

**Yes**, before a repository's `auto-approve-dependabot.yaml` moves to this release. Run
`a-novel repo update` from a stack that includes a-novel-kit/stack#765, so the caller grants the
`contents`, `attestations` and `packages` reads the engine requests. A reusable workflow cannot exceed
its caller's grant, and the engine fails to start without them.

Pin each first-party image that a composite-action input default names by digest, once:

```yaml
inputs:
  database_image:
    default: ghcr.io/a-novel/service-json-keys/database:v2.11.0@sha256:<digest>
```

Renovate then moves the digest with the tag. It pins the first-party images of compose files and
Dockerfiles on its own.

## What waits for a person

- A first-party npm version whose release predates `publish-actions/npm` v1.67.2, since its tarball
  carries no attestation.
- A first-party image pinned by tag alone.
- A version no release built. Treat it as an incident: find out who published it before approving.

The job summary names each version and the proof it lacks.
