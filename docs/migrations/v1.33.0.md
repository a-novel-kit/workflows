# Upgrading to v1.33.0

## Do I need to act?

Opt in when a platform should compare browser screenshots and store reports in private Google
Workspace Shared Drives. Existing callers keep their seven-day GitHub report artifacts until
`drive_ci_provider` is configured. Coverage artifacts and the Codecov contract remain compatible.
This guide targets the next minor release; use its published tag before merging a consumer.
The Drive helpers run on Node.js, with dependencies installed from their own pinned lockfile.

## Provision access first

Follow the [infrastructure runbook](https://github.com/a-novel/infra/blob/master/docs/runbooks/visual-test-storage.md).
Use an existing Shared Drive directory, with one CI directory per platform containing sibling
`references` and `results` folders. Share only those children with that platform's CI account:
Viewer on references and Contributor on results, with no Drive-level membership. Service accounts
need no Workspace user subscription; the organisation owns uploaded files.

Trusted maintenance must publish and permanently delete files in both folders. Google requires
`organizer` authority on a parent for permanent deletion. Verify whether the Workspace administrator
can confine that authority to the selected CI directory, including a disposable deletion probe and
an access check against unrelated content. Folder-only Manager authority has not been verified in
the target Workspace. Do not silently grant Manager access across an existing Drive: that broader
scope requires its owner's explicit approval. The action checks effective capabilities and scopes
all operations by folder and repository; that filtering does not limit the account's permissions.
Review external-account/nonmember sharing policy with the administrator before activation.
Use the same repository variables everywhere: `VISUAL_CI_PROVIDER`, `VISUAL_CI_ACCOUNT`,
`VISUAL_MAINTENANCE_PROVIDER`, `VISUAL_MAINTENANCE_ACCOUNT`, `VISUAL_REFERENCES_FOLDER` and
`VISUAL_RESULTS_FOLDER`. A new platform adds one infra map entry and its folder grants, then reuses
these callers. Pass folder IDs, not Shared Drive IDs. The action rejects My Drive, mismatched
platform parents, and reference write authority on candidate CI.
Add all six Drive inputs to `node-actions/test-playwright`: `drive_ci_provider`, `drive_ci_account`,
`drive_maintenance_provider`, `drive_maintenance_account`, `references_folder`, and `results_folder`.
Add `actions: read`, `pull-requests: read`, `statuses: write`, and `id-token: write` to the browser job.
Keep its ID `test-browser`, workflow path `.github/workflows/main.yaml`, name `main`, and default
branch `master`: the shared policy verifies those conventions. Allow about 30 minutes because
approved visual updates rerun the complete journey suite.

Pin Ubuntu (Studio uses `ubuntu-24.04`), Playwright, viewport, locale, timezone, fonts and theme.
Wait for product readiness, mask random identifiers and timestamps narrowly, and keep meaningful
functional assertions. Do not raise pixel tolerances to hide unstable rendering.

## Declare screenshots in the platform

When `PLAYWRIGHT_SNAPSHOT_DIR` is set, put native `expect.soft(page).toHaveScreenshot(name)`
checkpoints under that directory using a stable `snapshotPathTemplate`. Before each assertion,
append a test annotation with type `visual-snapshot` and description equal to its relative PNG
path beneath that directory. Declare every screenshot exactly once. The shared reporter verifies
that the annotations match the executed native assertions and that all selected tests completed.
Keep retries at zero; skips, expected failures, missing captures and incomplete suites cannot
publish a reference. Ignore `.visual/` in Git and container build contexts.

The action downloads the reference, compares without writing it, and packages the HTML report,
traces, screenshots and service logs. GitHub receives only the small component coverage artifact.
Download the private archive linked in the job summary and open its extracted report with
`pnpm exec playwright show-report playwright-report`. An approved change includes the original
comparison report and diff images in `.visual/comparison-report` as well as the regenerated batch.
Only allowlisted evidence paths enter the archive; never put credentials in those paths.

## Add trusted maintenance

Create `.github/workflows/visual-tests.yaml` on master with:

- `workflow_run` for completed `main` runs; `delete`; a daily scheduled sweep; and
  `pull_request_target` for `labeled`, `unlabeled`, `synchronize`, `opened`, `reopened`, `closed`.
- Set `run-name` to `Visual approval ${{ github.event.pull_request.number }} ${{ github.event.pull_request.head.sha }} ${{ github.event.pull_request.base.ref }} ${{ github.event.action }}`.
  Receipts verify this immutable run metadata, the trusted workflow path/event and successful
  approval job. A candidate status cannot impersonate a trusted label run.
- An approval job for `pull_request_target` using `generic-actions/approve-playwright`. Pass
  `github_token`; grant contents/pull-requests read and actions/statuses write. Serialize per PR,
  without cancellation, and allow 25 minutes for an active main run to finish before rerunning it.
- A separate cleanup job using `generic-actions/maintain-playwright`, passing `github_token`,
  `identity_provider`, `service_account`, `references_folder`, `results_folder`. Grant contents,
  actions and pull-requests read plus id-token write. Serialize this job across all events without
  cancellation. It reconciles current GitHub state, so coalesced events are safe.

These jobs execute only trusted default-branch action code. Never check out or execute PR code
from `pull_request_target` or `workflow_run`. The maintenance provider must enforce that boundary.
Keep approval separate so waiting for a rerun cannot delay storage cleanup. Guard the jobs until
Drive is configured. Update every workflows reference together to the published release tag.

## Review intentional changes

Create the `allow-screenshot-change` label. A human with repository write access applies it after
reviewing the failed comparison for the current PR head. The approval job records that head and
reruns main; a new commit invalidates approval, so remove and reapply the label after reviewing it.
Removing the label revokes approval and refreshes checks. Functional failures, incomplete capture,
missing master references and upload failures remain blocking.

Merge groups require completed visual proof for every included PR: either approval at its exact
head or an unchanged result against the same reference. Master carries that proof from the PRs'
merge times. Unknown direct commits cannot borrow another PR's approval. If master advanced since
an unchanged PR's proof, rerun that PR against the new reference before enqueueing it.

## Seed and verify

After the consumer and maintenance caller have landed, configure the six inputs and set `seed_sha`
to the exact reviewed current master SHA. Rerun that master main run. Empty storage is allowed only
for this explicit seed, with every functional test and capture successful. Unset `seed_sha` after
maintenance publishes the first reference. Ordinary runs fail if the reference is missing.

Master stages its locally validated archive directly in the protected references folder. Serialized
maintenance verifies completed successful `test-browser` and current master before promoting it.
It never copies candidate results into references. The old reference stays current until replacement
is complete, survives indefinitely without new master runs, and is permanently deleted afterward.
A successful master result is deduplicated against its reference. Each live branch keeps its latest
completed evidence, including failure diagnostics; pending uploads can briefly overlap. Merged or
deleted branches are removed permanently, with completion events and the daily sweep repairing races.
No blob overwrite, retained binary revision or Trash copy is used.

Verify a clean comparison, an unapproved pixel change, an approved pixel change, a functional failure
with the label, rerun recovery, branch merge/deletion during upload, stale master publication, and a
quiet reference beyond seven days. Live Drive federation and membership checks require the operator's
provisioned Workspace; offline HTTP-client and Chromium tests do not substitute for that activation check.
