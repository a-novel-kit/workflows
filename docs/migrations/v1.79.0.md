# Upgrading to v1.79.0

`publish-actions/sentry-release` records each release in Sentry with its commits and a `production`
deploy, from the job that cut it. `sentry-intake-run` boards each GitHub issue that Sentry's GitHub App
opens in Triage, typed Bug and labelled `sentry`.

## Do I need to act?

**Only in a repository with a Sentry project**, whose slug is the repository's name. Every other
repository calls neither and changes nothing.

## Record each release in Sentry

The release is `<repository>@<version>`, such as `service-authentication@1.2.3`, the name the deployed
service reports. The step reads the checkout `release-core` leaves, so it runs right after it in the
`cut` job. Give `release-core` an `id` and add the step:

```yaml
cut:
  needs: [plan]
  if: github.event_name != 'push' && !inputs.dry_run
  runs-on: ubuntu-latest
  environment: release
  permissions:
    contents: read
  steps:
    - id: release
      uses: a-novel-kit/workflows/publish-actions/release-core@v1.79.0
      with:
        # …unchanged.
    - uses: a-novel-kit/workflows/publish-actions/sentry-release@v1.79.0
      with:
        release_version: ${{ steps.release.outputs.version }}
        auth_token: ${{ secrets.SENTRY_AUTH_TOKEN }}
        # renovate: datasource=custom.sentry-cli depName=getsentry/sentry-cli
        version: "3.8.2"
        sha256: "c958865f9d4000183509ea21b1f04925d5390de6d8d87386b9e69f2b305070c3"
```

`SENTRY_AUTH_TOKEN` is a Sentry organization auth token, a secret of the repository's `release`
environment. Without it the step skips. A core member or an owner of the repository sets it, pasting
the token at the prompt:

```bash
gh secret set SENTRY_AUTH_TOKEN --env release --repo a-novel/service-authentication
```

The token names its organization and region, so a move to another Sentry organization replaces the
secret and nothing else. Sentry's GitHub App must be installed on the repository: it reads the commits
since the previous release. A Sentry failure turns the `cut` job red after the tag and the GitHub
Release exist, so the release itself is never held back.

The deploy is recorded at the cut, and infra deploys the release once its pin merges. A hotfix cut by
`release-line-run` records no Sentry release, so its release appears in Sentry with its first event,
without commits.

## Board the issues Sentry opens

A person creates a GitHub issue from a Sentry issue with the integration's button. Add a caller:

```yaml
# .github/workflows/sentry-intake.yaml
name: sentry-intake

on:
  issues:
    types: [opened]

jobs:
  intake:
    # The callee types and labels the issue; the board goes through the Agent App.
    permissions:
      issues: write
    uses: a-novel-kit/workflows/.github/workflows/sentry-intake-run.yaml@v1.79.0
    with:
      client_id: ${{ vars.AGENT_BOT_CLIENT_ID }}
      project_id: ${{ github.repository_owner == 'a-novel' && 'PVT_kwDOB9MxdM4BMh8r' || 'PVT_kwDOCy-nAM4BbtKH' }}
      kill_switch: ${{ vars.AGENT_KILL_SWITCH }}
    secrets:
      app_private_key: ${{ secrets.AGENT_BOT_PRIVATE_KEY }}
```

The Agent key comes from the repository's `governance` environment. A repository whose workflows
named no governance secret before gets that environment on the next `a-novel repo update`. The
`sentry` label comes from stack's managed labels on that same update.
