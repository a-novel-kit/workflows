# Upgrading to v1.52.0

`v1.52.0` stops `build-actions/docker` and `docker-job` from tagging every branch build. Each pull
request push used to move a `pr-<N>` tag, each merge-queue group left a permanent
`gh-readonly-queue-…` tag, a push to any other branch left a tag named after it, and every build's
attestation added a `sha256-<digest>` tag.

Now an image is tagged only on a push to the default branch (`master`, unchanged), a release, or a
pull request labeled `with-feature-env`, which moves its `pr-<N>` tag to the labeled head. Every other
build is pushed by digest alone, so the jobs of its run still pull it by digest, and its attestation
stays in GitHub's attestation store, where `gh attestation verify` finds it.

The label tags the head it was added on. A push builds untagged, and the managed `feature-env.yaml`
workflow removes the label; add it again to tag the new head.

## Do I need to act?

**Run `a-novel repo update` on each repository that builds images.** It provisions the
`with-feature-env` label and the `feature-env.yaml` workflow that removes it after a push. Without the
workflow, a push still builds untagged, but the label stays on the pull request until someone removes
it.

**Trigger the build workflow on `labeled`.** Adding the label tags anything only when it starts a
build. The services' `main.yaml` already runs on `labeled`:

```yaml
on:
  pull_request:
    types: [opened, synchronize, reopened, labeled, unlabeled]
```

A repository whose `main.yaml` runs on branch pushes only keeps building untagged and cannot tag a pull
request yet.

## What reviewers see

- No new `pr-<N>`, branch, merge-queue or `sha256-<digest>` tags on unlabeled builds. Tags already in
  the registry are left as they are.
- After a push, `with-feature-env` is gone from the pull request, and `pr-<N>` still names the last
  labeled head.
